# Как работает приложение

Документ описывает поведение UI: какие кадры уходят в порт при нажатии кнопок,
что происходит в разделах GF и CAL, как разбираются ответы устройства и когда
элементы управления доступны.

Точки в коде: `app.py` (вся логика команд), `device/protocol.py` (формат кадров),
`device/connection.py` (порт и поток чтения), `widgets/` (виджеты).

## 1. Запуск и подключение

1. `main.py` → `app.main()`: читается `config.ini` (`settings.AppConfig.load()`).
   Битый конфиг не мешает запуску — берутся значения по умолчанию, а в статус-бар
   пишется `config error, using defaults — …`.
2. Окно показывается, и только потом (`QTimer.singleShot(0, …)`) стартует
   подключение — первая отрисовка не ждёт открытия порта.
3. `ConnectionController` открывает порт в отдельном потоке с ретраями
   (секция `[retry]` в `config.ini`). Состояния: `connecting` / `connected` /
   `failed`. Статус-бар показывает цветную точку и текст, тултип — полное
   сообщение драйвера. Кнопка справа в статус-баре: **CANCEL** во время попыток,
   **RETRY** после неудачи.
4. После успешного подключения запускается поток чтения: байты собираются в
   буфер, `protocol.take_responses()` вырезает из него целые кадры ответов,
   каждый кадр приходит в `MainWindow._on_frame()`.

Закрытие окна (`closeEvent`) останавливает потоки и освобождает порт.

## 2. Формат кадров

Команда, 11 байт:

```
fe ed | platform ID | pad ID | cmd | extra1 | extra2 | CRC_LOW CRC_HIGH | 04 04
```

CRC — CRC-16/CCITT-FALSE (poly 0x1021, init 0xFFFF) по пяти байтам от
`platform ID` до `extra2`, младшим байтом вперёд.

Ответы приходят с собственным заголовком `be ef` и бывают двух длин:

```
be ef | platform ID | pad ID | 8 байт значений | CRC_LOW CRC_HIGH | 04 04   (16 байт)
be ef | platform ID | cmd    | 0x06            | CRC_LOW CRC_HIGH | 04 04   (9 байт)
```

Длинный кадр — это либо восемь factory GF, либо восемь показаний; отличаются
они только контекстом: показания приходят между Start и Stop, GF — в остальное
время (`MainWindow._on_frame`, флаг `self._running`). Короткий кадр — ACK на
команду сохранения, pad ID в нём нет.

Коды команд (`device/protocol.py`):

| Код | Константа | Смысл |
| --- | --- | --- |
| `0x50` | `CMD_PADS_CALIBRATION_START` | начать прогон |
| `0x51` | `CMD_PADS_CALIBRATION_STOP` | остановить прогон |
| `0x52` | `CMD_PADS_GET_FACTORY_GF` | запросить factory GF пада |
| `0x53` | `CMD_PADS_SAVE_FACTORY_GF` | сохранить GF (канал в `extra1`, значение в `extra2`) |
| `0x55` | `CMD_PADS_SAVE_CF` | сохранить calibration factor (канал в `extra1`, значение в `extra2`) |

`pad ID = 0` (`NO_PAD`) означает команду всей платформе.

## 3. Общие требования к отправке

Перед любой командой берётся **Platform ID** из левой панели
(`MainWindow._platform_id()`): целое 0–255. Если поле пустое или значение вне
диапазона — ничего не отправляется, в статус-баре `set a platform ID first`.

Platform type (SINGLE / DOUBLE) задаёт число падов: 1 или 2. Команды «на каждый
пад» перебирают пады с номерами 1..N.

Каждый отправленный кадр логируется (`tx fe ed …`) и попадает в тултип
статус-бара в виде hex-дампа.

## 4. Кнопки левой панели

### Read

`MainWindow._on_read()` → `_send_per_pad(get_factory_gf, "read")`.

- На каждый пад уходит `CMD_PADS_GET_FACTORY_GF` (`0x52`), `extra1 = extra2 = 0`.
- Между кадрами разных падов выдерживается пауза `PAD_GAP = 0.2 с`
  (`time.sleep`, поэтому на время паузы GUI подмораживается — в коде помечено
  комментарием `ponytail:`).
- Успех: `read sent for N pad(s)`. Ошибка сборки кадра или записи в порт
  прерывает цикл: `read failed on pad K — …`.
- Ответы приходят асинхронно, по кадру на пад, и раскладываются в поля GF
  (см. раздел 6).

### Write

`MainWindow._on_write()` смотрит, какой раздел открыт:

- **GF** → `_send_per_pad(write_factory_gf, "write")`: на каждый пад уходит
  `CMD_PADS_SAVE_FACTORY_GF` (`0x53`) с `extra1 = extra2 = 0`, то есть команда
  «зафиксируй то, что уже передано по каналам». Та же пауза 0.2 с между падами.
- **CAL** → `_write_calibration_factors()`, последовательность с подтверждениями
  (см. раздел 7).

### Start / Stop

Одна кнопка-защёлка (`setCheckable(True)`), текст меняется START ↔ STOP
(`MainWindow._on_start_toggled`).

- Нажатие при отжатом состоянии → `CMD_PADS_CALIBRATION_START` (`0x50`),
  `pad ID = 0`. Повторное нажатие → `CMD_PADS_CALIBRATION_STOP` (`0x51`).
- Кадр уходит только если порт в состоянии `connected`. Если отправка старта не
  удалась, кнопка сама отжимается (флаг `_reverting` не даёт при этом отправить
  «стоп») — состояние UI не расходится с устройством.
- Пока прогон идёт (`_running = True`), приходящие длинные кадры трактуются как
  показания (знаковые байты), а не как GF.
- Прогон принудительно завершается, если пользователь уходит из раздела CAL или
  если соединение пропало: кнопка отжимается, и по этому же пути уходит `0x51`,
  если порт ещё жив.

## 5. Доступность элементов (`_apply_controls`)

| Элемент | Когда доступен |
| --- | --- |
| Read, Write | порт подключён и прогон не идёт |
| Start/Stop | порт подключён и открыт раздел CAL |
| Platform ID, Platform type | только вне раздела CAL |
| Степперы `–` / `+` у каналов | только во время прогона |

Логика: платформа выбирается в разделе GF и фиксируется на время калибровки;
Read/Write не должны вклиниваться в поток показаний; степперы имеют смысл
только когда есть что подкручивать вживую.

## 6. Раздел GF (FACTORY GF SETUP)

Переключатель GF/CAL находится справа в заголовке рабочей области
(`widgets/workspace.py`, `PadView.view_toggle`).

Что показано: карточка пада с каналами ch0, ch1, ch2, ch4, ch5, ch6 — так, как
они расположены на плите. У каждого канала одно **редактируемое** поле —
factory gain factor.

- Поле — `NumericField` с диапазоном `GF_MIN = 10` … `GF_MAX = 200`.
- Значение фиксируется по Enter или при потере фокуса, и **только если оно
  изменилось**: повторный ввод того же числа командой не считается.
- При фиксации уходит `CMD_PADS_SAVE_FACTORY_GF` (`0x53`) с
  `pad ID = номер пада`, `extra1 = номер канала`, `extra2 = значение`.
  Статус: `pad 1 ch2 gf=57 sent`.
- Если отправить не удалось (нет Platform ID, ошибка порта, значение не прошло
  протокольную проверку) — поле откатывается (`NumericField.rollback()`): число
  остаётся на экране, но не считается доставленным, поэтому повторный ввод снова
  будет командой. Статус: `gf not sent — …`.
- Нечисловой или выходящий за диапазон ввод отклоняется валидатором и
  сообщается как `gf must be 10–200, '…' ignored`.

Ответ на **Read** (`parse_response`, беззнаковые байты) раскладывается по
номерам каналов: значение с индексом *i* принадлежит `ch<i>`. Оно одновременно:

1. подставляется в поле GF соответствующего канала;
2. сохраняется как **база калибровки** для раздела CAL
   (`calibration_factor_single` / `calibration_factor_double`);
3. подставляется в отображаемый calibration factor этого канала.

Статус: `pad 1 gf read`, тултип — hex-дамп кадра.

Кнопка **Write** в этом разделе просто говорит устройству зафиксировать
переданные GF (по кадру на пад, `0x53` без канала и значения).

## 7. Раздел CAL (CALIBRATION FACTOR SETUP)

Что показано у каждого канала: кнопка `–`, поле показания, кнопка `+`, а под
ними — текущий calibration factor. Рядом с падом — график cop; у DOUBLE это
один общий «total cop» рядом с первым падом плюс колонка Fx/Fy/Fz у каждого пада.

### Степперы

- `–` / `+` меняют calibration factor на единицу в пределах
  `CAL_MIN = 10` … `CAL_MAX = 200` (`widgets/pad_card.py`).
- Доступны только во время прогона.
- Достижение края диапазона ничего не отправляет, а сообщает в статус-бар:
  `pad 1 ch0 is at its highest calibration factor (10–200)`.
- Степпер меняет **показываемый** фактор, а не базу, прочитанную с устройства.
  В порт при этом ничего не уходит — значения отправляются кнопкой Write.

### Показания

Каждый длинный кадр, пришедший во время прогона, разбирается как восемь
знаковых показаний и масштабируется по каналу (`PadView.set_reading`):

```
показание_на_экране = raw * текущий_calibration_factor / (база_GF * 100)
```

где `база_GF` — то, что пришло по Read для этого канала. Если база нулевая
(канал устройством не используется), показывается `0.0`. Кадры показаний в
статус-бар не пишутся — их слишком много; они уходят в лог на уровне DEBUG.

### Write в разделе CAL

`_write_calibration_factors()` строит очередь кадров и шлёт их **по одному, с
ожиданием подтверждения**:

1. для каждого пада и каждого показанного канала — `CMD_PADS_SAVE_CF` (`0x55`),
   `extra1 = канал`, `extra2 = calibration factor`;
2. затем для каждого пада — `CMD_PADS_SAVE_CF` с `extra1 = extra2 = 0`, то есть
   «сохрани принятые значения».

Правила последовательности:

- Следующий кадр уходит только после ACK (`be ef … 0x55 0x06 …`) на предыдущий
  (`_on_cf_ack`). ACK с чужим platform ID игнорируется.
- Таймаут ожидания — `ACK_TIMEOUT = 200 мс`. Если ответа нет, оставшаяся часть
  очереди сбрасывается: `no answer to pad 1 ch3 cf=42 in 200ms, write stopped`.
- Повторное нажатие Write, пока очередь не пуста, отклоняется:
  `write already in progress`.
- По завершении очереди: `calibration factors written`.

## 8. Переключение GF ↔ CAL и SINGLE ↔ DOUBLE

Оба переключателя пересоздают карточки падов (`PadView._rebuild()`), поэтому
значения хранятся отдельно от виджетов и восстанавливаются после пересборки:

- `_factors` — введённые и прочитанные factory GF (поля раздела GF);
- `_shown_factors` — то, что показывает поле calibration factor, с учётом
  степперов;
- `calibration_factor_single` / `calibration_factor_double` — база для
  масштабирования показаний, меняется только чтением с устройства.

Уход из CAL при активном прогоне отжимает Start и отправляет `0x51`.

## 9. Обработка входящих кадров (`MainWindow._on_frame`)

1. Кадр длиной 9 байт → ACK. Разбирается `parse_ack()`; при несовпадении
   platform ID игнорируется, иначе продвигает очередь Write раздела CAL.
2. Кадр длиной 16 байт → `parse_response(signed=self._running)`: во время
   прогона это показания (знаковые), иначе factory GF (беззнаковые).
3. Кадр с чужим platform ID отбрасывается, факт пишется в лог.
4. Кадр с битым CRC или неверной длиной → `ProtocolError`, статус
   `bad answer — …` или `bad ack — …`, hex-дамп в тултипе.

## 10. Что пока не подключено к данным

- Колонки Fx / Fy / Fz у падов и блок **Total** (Fx, Fy, Fz, xcop, ycop) в левой
  панели — статические заглушки, устройство их не заполняет.
- Графики cop (`widgets/cop_plot.py`) рисуют сетку, но не точку давления.
- Пустое состояние `Placeholder` (индекс `EMPTY` в `QStackedWidget`) существует,
  но рабочая область всегда показывает раздел с падами.
