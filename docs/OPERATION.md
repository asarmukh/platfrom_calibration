# Как работает приложение

Документ описывает поведение UI против ТЗ: какие кадры уходят в порт, что
происходит в разделах GF и CAL, как разбираются ответы и когда элементы
управления доступны. Ссылки вида «ТЗ 5.1» указывают на раздел ТЗ.

Точки в коде: `app.py` (логика команд), `calc.py` (силы и центр давления),
`device/protocol.py` (формат кадров), `device/connection.py` (порт и поток
чтения), `widgets/` (виджеты).

## 1. Запуск и подключение (ТЗ 3)

1. `app.main()`: читается `config.ini`. Битый конфиг не мешает запуску — берутся
   значения по умолчанию, а в статус-бар пишется `config error, using defaults`.
2. Окно показывается, и только потом стартует подключение — первая отрисовка не
   ждёт открытия порта.
3. `ConnectionController` открывает порт в отдельном потоке с ретраями
   (секция `[retry]`). Состояния: `connecting` / `connected` / `failed`.
4. Поля factory GF и calibration factor стартуют со значением **10**, массивы
   `calibration_factor_single[8]` и `calibration_factor_double[2][8]` тоже
   заполнены десятками.
5. **Platform type стартует ненажатым**: ни SINGLE, ни DOUBLE не подсвечены —
   какая платформа на стенде, решает оператор, а не значение по умолчанию.
   Как только тип выбран, в рабочей области появляются карточки падов — одна
   для SINGLE, две для DOUBLE — со значениями по умолчанию (ТЗ 3б).
6. **Пока не введён Platform ID, никаких действий не выполнить**: карточки
   видны, но неактивны, кнопки Read / Write / Start погашены. Показать значения
   — не действие, поэтому они на экране; отправить кадр — действие, поэтому
   до ввода ID ничего не уходит. Очистка ID снова гасит интерфейс.

Закрытие окна освобождает порт.

## 2. Формат кадров (ТЗ 2, 7)

Команда, 11 байт:

```
fe ed | platform ID | pad ID | cmd | extra1 | extra2 | CRC_LOW CRC_HIGH | 04 04
```

CRC — CRC-16/CCITT-FALSE (poly 0x1021, init 0xFFFF), младшим байтом вперёд, по
пяти байтам от `platform ID` до `extra2`. У ответа CRC считается так же — по
всему, что лежит между заголовком и самим CRC.

Ответы приходят с заголовком `be ef` и бывают трёх длин:

```
be ef | platform ID | cmd    | 0x06               | CRC | 04 04    9 байт  — ack
be ef | platform ID | pad ID | uint8_t  factor[8] | CRC | 04 04   16 байт  — факторы
be ef | platform ID | pad ID | int16_t reading[8] | CRC | 04 04   24 байта — показания
```

Показания — знаковые 16-битные, младшим байтом вперёд. Ни `04 04`, ни `be ef`
не годятся как разделители: обе пары — допустимые значения `int16`, поэтому
кадр опознаётся только по длине и CRC (`protocol.take_responses`).

16-байтный кадр отвечает и на `GET_FACTORY_GF`, и на `GET_CF`, и различить их
внутри кадра нечем — приложение помнит, какой запрос оно отправило
(`MainWindow._pending_read`).

Коды команд:

| Код | Константа | Смысл |
| --- | --- | --- |
| `0x50` | `CMD_PADS_CALIBRATION_START` | начать прогон |
| `0x51` | `CMD_PADS_CALIBRATION_STOP` | остановить прогон |
| `0x52` | `CMD_PADS_GET_FACTORY_GF` | запросить factory GF пада |
| `0x53` | `CMD_PADS_SAVE_FACTORY_GF` | сохранить GF (канал в `extra1`, значение в `extra2`) |
| `0x54` | `CMD_PADS_GET_CF` | запросить calibration factor пада |
| `0x55` | `CMD_PADS_SAVE_CF` | сохранить calibration factor |

`pad ID = 0` (`NO_PAD`) означает команду всей платформе.

## 3. Движок последовательностей

Все многокадровые обмены идут через один механизм (`_Sequence`, `MainWindow._run`):

- `gap_ms` — пауза между покадровыми командами разным падам, `PAD_GAP = 200 мс`
  (ТЗ 4.2, 4.3, 5.2). Пауза выдерживается таймером, GUI при этом живой.
- `await_cmd` — следующий кадр уходит только после acknowledge на предыдущий.
  Нет ответа за `ACK_TIMEOUT = 500 мс` — остаток очереди сбрасывается, в
  статус-бар пишется, на каком кадре всё встало.
- `freeze` — на время обмена весь GUI неактивен (ТЗ 4.3, 5.1). Снимается по
  последнему acknowledge, по таймауту и по ошибке записи в порт.

Каждый отправленный кадр логируется как `tx …`, каждый принятый — как `rx …`
с расшифровкой. Показания пишутся только на уровне DEBUG: их слишком много.

## 4. Раздел GF — FACTORY GF SETUP (ТЗ 4)

У каждого канала одно редактируемое поле — factory gain factor, диапазон
`GF_MIN = 10` … `GF_MAX = 200`.

**Ввод значения (4.1).** Значение фиксируется по Enter или при потере фокуса и
только если изменилось. Уходит `0x53` с `pad ID` пада, `extra1 = канал`,
`extra2 = значение`. Если отправить не удалось, поле откатывается
(`NumericField.rollback`) — число остаётся на экране, но не считается
доставленным.

**READ (4.2).** По кадру `0x52` на пад, `PAD_GAP` между падами,
acknowledge на эту команду не приходит. Пришедшие факторы раскладываются в поля
GF по номеру канала.

Factory GF нужен только для контроля оператором: он **не** участвует в
масштабировании показаний и не трогает `calibration_factor_*`.

**WRITE (4.3).** По кадру `0x53` с нулями на пад, с паузой `PAD_GAP`, каждый
ждёт своего acknowledge, GUI неактивен до последнего.

## 5. Раздел CAL — CALIBRATION FACTOR SETUP (ТЗ 5)

У каждого канала: кнопка `–`, поле показания, кнопка `+`, под ними текущий
calibration factor. Рядом с падом — график cop; у DOUBLE это один общий
«total cop» рядом с первым падом плюс колонка Fx/Fy/Fz у каждого пада.

**READ (5.2).** По кадру `0x54` на пад, `PAD_GAP` между падами, acknowledge
нет. Ответ кладётся и в поля calibration factor, и в
`calibration_factor_single[8]` / `calibration_factor_double[2][8]` — это
единственное, что меняет базу масштабирования.

**WRITE (5.1).** Для каждого канала уходит `0x55` с `extra1 = канал`,
`extra2 = показанный фактор`, по очереди на пад 1 и пад 2 (channel-major — так
читается «pad ID = 1 и 2 по-очереди» внутри цикла по каналам). После всех
каналов — по одному закрывающему `0x55` с нулями **на каждый пад**: в ТЗ
написан один кадр с `pad ID = 1`, но тогда второму паду никто не велит
сохраниться. Каждый кадр ждёт acknowledge, GUI неактивен до последнего.

**START / STOP (5.3, 5.4).** Одна кнопка-защёлка. `0x50` и `0x51` уходят с
`pad ID = 0`. На старт acknowledge не приходит — вместо него идёт поток
24-байтных показаний.

**Степперы (5.5).** `–` / `+` меняют показанный calibration factor на единицу в
пределах `CAL_MIN = 10` … `CAL_MAX = 200`. В порт при этом ничего не уходит:
значения отправляются кнопкой Write. База, прочитанная с устройства, не
меняется.

**Показания (5.3).** Каждый 24-байтный кадр разбирается как восемь знаковых
значений и масштабируется по каналу:

```
показание = raw * текущий_calibration_factor / (база_cf * 100)
```

Кадры копятся, а на экран попадают по таймеру раз в `RENDER_INTERVAL = 50 мс`,
чтобы поток не забивал GUI-поток. Нулевая база даёт `0.0`.

Показания, пришедшие вне прогона (платформа осталась включённой с прошлого
сеанса), вызывают однократный `0x51`.

## 6. Силы и центр давления (ТЗ 6)

Считает `calc.py` — по масштабированным показаниям, не по сырым отсчётам.

SINGLE, в блоке TOTAL:

```
Fx = ch6,  Fy = ch0,  Fz = ch1 + ch2 + ch4 + ch5
xcop = 10 * (ch1 - ch2 + ch5 - ch4) / Fz
ycop =  7 * (ch1 + ch2 - ch4 - ch5) / Fz
```

DOUBLE — Fx/Fy/Fz каждого пада в колонке слева от него, а в TOTAL суммы и

```
xcop = 10 * ((ch1-ch2+ch5-ch4)₁ + (ch1-ch2+ch5-ch4)₂) / Fz_total
ycop = (21*(ch1+ch2)₁ + 7*(ch4+ch5)₁ - 7*(ch1+ch2)₂ - 21*(ch4+ch5)₂) / Fz_total
```

В ТЗ знаменатель ycop записан как `Fz`; это опечатка — при нагрузке целиком на
одном паде деление шло бы на ноль другого.

Коэффициенты 10, 7 и 21 — координаты Fz-сенсоров из рисунка ТЗ, так что cop
получается в сантиметрах от центра платформы. При `Fz = 0` центр давления не
определён: в полях `—`, точка с графика убирается.

## 7. Доступность элементов (`_apply_controls`)

| Элемент | Когда доступен |
| --- | --- |
| Карточки падов видны | выбран тип платформы |
| Карточки падов активны | плюс: введён Platform ID, не идёт запись с ожиданием ack |
| Read, Write | плюс: порт подключён, прогон не идёт |
| Start/Stop | плюс: порт подключён, открыт раздел CAL |
| Platform ID, Platform type | вне раздела CAL и вне записи |
| Степперы `–` / `+` | в разделе CAL |

Прогон принудительно завершается, если оператор уходит из раздела CAL или
если соединение пропало.

## 8. Переключение GF ↔ CAL и SINGLE ↔ DOUBLE

Оба переключателя пересоздают карточки падов (`PadView._rebuild`), поэтому
значения хранятся отдельно от виджетов:

- `_factors` — factory GF (поля раздела GF);
- `_shown_factors` — то, что показывает поле calibration factor, со степперами;
- `calibration_factor_single` / `calibration_factor_double` — база
  масштабирования, меняется только чтением `0x54`;
- `_readings` — последний масштабированный кадр каждого пада.

## 9. Обработка входящих кадров (`MainWindow._on_frame`)

1. 9 байт → acknowledge: двигает текущую последовательность, если код команды
   совпал с ожидаемым.
2. 16 байт → факторы: GF или CF в зависимости от того, что запрашивали. Кадр,
   который никто не запрашивал, игнорируется.
3. 24 байта → показания.
4. Кадр с чужим platform ID отбрасывается и пишется в лог.
5. Битый CRC или неверная длина → `ProtocolError`, статус `bad answer — …`,
   hex-дамп в тултипе.

## 10. Тесты

`pytest` — 84 теста, разложенные по разделам ТЗ:

- `tests/test_protocol.py` — раскладка кадров, CRC, разбор всех трёх типов
  ответов, пересинхронизация потока;
- `tests/test_calc.py` — формулы раздела 6, включая проверку, что нагрузка на
  один сенсор даёт его координаты;
- `tests/test_sequences.py` — что уходит в порт по каждой кнопке, порядок
  кадров, ожидание acknowledge, блокировка GUI, шкалирование показаний.

`python tests/render_views.py` рисует состояния окна в PNG для глазной проверки.
